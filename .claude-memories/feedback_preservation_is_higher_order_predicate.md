**User correction (2026-06-27):** `Preserving('p)` as a **type relation** (type class) is the WRONG abstraction. A type relation is coherent — one instance per type — so `Preserving(A)` can hold only ONE method `f: A→A`. But a datatype `A` can have MANY functions that preserve `'p` (`f₁, f₂, …`); `overlap` makes resolution ambiguous and splitting into `Preserving₁/₂(A)` is nonsense. **Preservation is a property of a FUNCTION, not of a type** → it must be a **higher-order predicate** `preserving(f)`, each function checked independently.

**Rule:** type relations (= type classes, see [[feedback-type-relation-is-typeclass]]) are for the **canonical-per-type structure** (Ord, IntegerLike — one structure per type). Anything that is "per-function" / "per-value" (preservation, and likely similar properties) belongs as a **higher-order predicate** parametric in the relevant `'p`/`'q` (the ② generic predicate parameters), typically taking a **refinement-typed function** argument `{u:A|'p} -> {v:A|'q}`.

**Consequence for landed work:** the `adsmt-class/src/preserving.rs` `Preserving('p)` relation + its engine test were **RETIRED (commit `fa7deca`)**. The generic type-relation `'p` data model (pred_params/Instance::preds/Dict::pred, commit `1c3b63b`) is **KEPT** as neutral infra (a genuine type relation MAY carry a predicate parameter; its 4 resolve.rs tests use a synthetic relation, not Preserving). The ② fn-level generic `'p`/`'q` machinery stays.

**Proposed surface (user example, semantics being pinned):** `preserving` as a higher-order predicate using a `solve … by …` construct:
```
fn preserving(f: {u: A | 'p(u)} -> {v: A | 'q(v)}) -> Bool:
    let result = solve forall {x: A | 'p(x)}. 'p(f(x))
                 by:   forall {y = f(x) | 'p(x)}. 'q(y) ==> 'p(y)
    return result
```
