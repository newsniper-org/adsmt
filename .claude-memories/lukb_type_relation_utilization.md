**User asked (2026-06-27):** has the lukb "type relation" (`Nat⊂WNat⊂Int⊂Real`, 0∉Nat, injections, refinement binders) been properly utilized? Could the residual lu↔z3 disagreements be caught via it? Multi-agent audit (5 layer-readers + adversarial verify + synthesis) verdict:

**NOT properly utilized — the type relation is TYPECHECK-ONLY, dropped before the solver.** It is REPRESENTED (kernel `adsmt-ir/src/theory.rs:128-150` postulates the 4 sorts + 6 injections `nat2int`/`wnat2int`/`int2real`/…; lukb `elab.rs:413-422` inserts up-cast coercions at operand boundaries so the lattice SHAPES well-typed terms). But its DEFINING FACTS never exist as axioms/assertions:
- **Positivity is never synthesized** — `Nat ⟹ x≥1`, `WNat ⟹ x≥0` are a DOC COMMENT (`theory.rs:18-27`), not axioms. `elab_quant` (lukb `elab.rs:231-291`) conjoins ONLY user-written refinement guards into a binder, never an implicit `n≥1` for a `Nat` binder. The design (`LUKB_SUCCESSOR_SURFACE.md:471-485`) pins the Fermat encoding's soundness on "`x:Nat` already means ≥1" — but that knowledge is **missing**.
- **Flow is severed at #325 lowering** — `adsmt-ir-lower/src/lower.rs` maps every Nat/WNat sort to an uninterpreted `CType::const_` and every injection to an uninterpreted EUF function (`try_arith` hardcodes only `th::INT_*`/`th::REAL_*`, returns `None` for the injections → EUF fall-through, `lower.rs:13-14,383-443,663-675`). So a theory-Nat variable reaches the engine as an **opaque EUF element with zero arithmetic content**.
- SMT-LIB face is confirmed FLAT-sort (installs only `install_int_real`, `adsmt-ir-smtlib/elab.rs:136`; native `convert.rs` registers all sorts uniformly) — so the type relation is UNIQUE to lukb and never on the differentialed path (this is why [[lu-vs-z3-disagreement-analysis]] found no lu-better cases).

**Could it catch the residual disagreements? — IMPORTANT CORRECTION:** the two NAMED residuals are NOT type-relation problems (category error to expect it):
- (a) datatype `b≠zero ∧ pred b=b`: the `Nat` there is a USER-DECLARED `(declare-datatype Nat …)` inductive, NOT the arithmetic `theory::NAT` sort. It's a datatype acyclicity/single-survivor gap in `adsmt-theory` (#331 residual), unrelated to positivity.
- (b) LIA `0<x<2 ∧ x≠1`: `x:Int`, no Nat/WNat involved — a pure LIA integer-feasibility/branching gap (#337/#289).
- **WHERE it WOULD bite = the broad Nat/WNat-positivity class** — any goal implicitly relying on a theory-Nat being ≥1 (Fermat-style) is currently UNDECIDABLE because the Nat var is opaque EUF. Asserting `nat2int(x)≥1` / `wnat2int(x)≥0` lets LIA discharge exactly those.

**Biggest lever (the actual opportunity, soundness-MONOTONE):** synthesize Nat/WNat positivity as a guard + route the injections through arithmetic instead of EUF, so theory-Nat vars reach LIA/LRA with their defining constraint. Adding a TRUE hypothesis can only turn sat/Unknown→unsat, never spurious-sat (the dual-safe direction of [[feedback_soundness_opaque_fallback]]). **Caveat:** its effect is only realized once the lukb→solve VERDICT path is wired (gated on #325 being exercised end-to-end). Injection INJECTIVITY/identity axioms (rec. 4) are NOT trivially monotone (EUF/arith-congruence interaction) → require a z3-differential before trusting any new unsat. Tracked as a task.

**UPDATE 2026-06-27 — the `IntegerLike(Peano)` arith bridge LANDED + is SOUND (commit `b76ab2b`), overriding the design's "ship inert" recommendation (the user required it be made fully sound, not bypassed).** Note: in this project the user calls these type-CLASSES **"type relations"** (each instance, single- or multi-parameter, is a relation between types/theories). The bridge realises `IntegerLike(Peano)`: a Peano datatype `S = base | succ(sel:S)` (free algebra ≅ ℕ) now flows into LIA via fresh integer image vars `!peano_img!t`, with the sound image equalities `img(base)=0`, `img(succ s)=img(s)+1`, congruence, and the GATED `img(pred s)=img(s)−1` (only for an `s` forced succ-shaped, so `pred(base)` never leaks `−1`). The PREREQUISITE that makes it sound = `DatatypeDecl.field_sorts` (threaded from parser+lowering) → the **conservative `peano_shape` recognizer FAILS CLOSED** without field sorts and rejects `wrap(Int)` (foreign field) + mutual recursion (the over-fire the audit flagged). Also extended LinArith to parse **offset equalities `x = y ± k`** (the form the bridge emits). **Validated: 12000+ datatype z3-differential queries → 0 false-unsat**; adversarial wrap(Int)/mutual-rec/3-ctor correctly NOT bridged. So the type relation now ACTIVELY decides Peano arithmetic — the first member of the [[four-way-interlock-design-intent]] *Like family wired into the solver. **UPDATE 2026-06-28 (`5449e33`) — the Nat/WNat *arithmetic*-sort positivity (#338) is now DONE too: the biggest lever above is USED.** The lower→solve path decides Nat/WNat positivity end-to-end (`c:Nat ∧ c<1` → `unsat`); the fix was a one-line orientation swap in `Lowerer::positivity` (`(<= lo v)` → `(>= v lo)`, the canonical `(op var literal)` form the bare LinArith claims — literal-on-left was reaching the solver uninterpreted → `Unknown`). z3-differential 7/7 engine==z3 (the "require a z3-differential before trusting any new unsat" caveat satisfied). So the type relation is no longer TYPECHECK-ONLY for the Nat/WNat arithmetic carriers. See [[cic_hol_lowering]], [[nat_wnat_refinement_collapse]].
