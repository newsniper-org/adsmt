**User directive (2026-06-27):** for any lu-smt↔z3 disagreement where lu shows a *better* result than z3, find the reason separately and record it.

**Finding — there are NONE in the SMT-LIB fragment.** Across 10000+ randomized z3-differential queries this session (pure-SAT 6500, datatype 7200+, LIA/LRA+eq 4000, mixed-edge 2400), EVERY lu↔z3 disagreement was one of:
- **lu false-sat** (lu `sat`, z3 `unsat`) — a lu COMPLETENESS gap, z3 correct. Conservative/verifier-safe direction. Examples: datatype acyclicity/exhaustiveness (now fixed, #331), the LIA singleton-disequality gap below.
- **lu `unknown`** (lu abstains, z3 decides) — lu LESS complete (nonlinear `x·y>5 ∧ x·y<3`, symbolic-RHS comparisons). z3 strictly better.
- **0 z3-wrong**, **0 z3-unknown-but-lu-decided**, **0 lu false-unsat** (after this session's fixes).

**WHY lu can never beat z3 here:** the **SMT-LIB face** (`adsmt-ir-smtlib` / native `convert.rs`) lowers to the SAME flat-sort semantics z3 uses (`Int`/`Real`, no subtyping — see [[cic_hol_lowering]]'s Var/Const leaf rule). On identical semantics a sound solver can only be EQUAL or LESS complete than z3, never MORE correct. So the differential is a pure soundness/completeness gate, and "lu better" is structurally impossible on this path.

**WHERE "lu better than z3" WOULD live — the lukb TYPE RELATION.** lu-kb's richer typed semantics (`Nat ⊂ WNat ⊂ Int ⊂ Real` with **0 ∉ Nat**, explicit injections, refinement-constrained binders — see [[verus_emits_lukb_surface]]) add constraints a flat SMT-LIB encoding lacks. e.g. Fermat over `x y z: Nat` is sound *because* Nat excludes 0 (no trivial `(0,k,k)`); the flat-Int version needs explicit `x>0 ∧ y>0 ∧ z>0` guards or it's falsifiable. So lu-kb is "more precise w.r.t. the intended typed semantics" — but **that richness is in the lukb FACE, which has no solver path yet** (gated on CIC→HOL #325). The SMT-LIB differential never exercises it. This is the concrete motivation for the user's directive-2 question ("has the type-relation been properly utilized?") — answer so far: it is NOT used in any solving path, only in the lukb face's elaboration/printing.

**Spun-off conservative gap (new this session):** `0 < x < 2 ∧ x ≠ 1` (Int) → lu `sat`, z3 `unsat` — LIA tightens to the singleton `x ∈ [1,1]` but never tests the `x ≠ 1` disequality against it. Same flavour as the #336 EUF↔LRA gap but single-variable. Conservative direction; tracked as a task. See [[feedback_z3_differential_for_unsat_trust]].

**CORRECTION (2026-06-27) — the "every disagreement is lu-CONSERVATIVE" claim had a HOLE: native LIA two-variable comparisons could false-SAT (lu `sat`, z3 `unsat` = lu WRONG, non-conservative). The earlier corpus missed it because it never generated bare two-var comparison CHAINS** (`(<= a b)`, `(< a b)`, var-var `(= a b)`/`≠`) — it leaned on var-vs-constant atoms. Found while building the `EngineLawProver` order laws ([[numberlike-family-design]]); three LinArith bugs (all false-sat, reachable from plain SMT-LIB in BOTH default + oxiz builds since delegation only fires on native `Unknown`, never `Sat`): (1) `existing_dominates_le` checked only the existing side → an FM-derived `a−c≤0` dropped as redundant vs a stored `a−c>0` (transitivity, #340); (2) the FM closure only chains `≤`/`<` → a chain through a `≥`/`>` link never closed (`b≥c ∧ b<a ∧ c>a`); (3) var-var `a≠b` left to UF, never checked vs an arith-pinned `a=b` (antisymmetry, #341). FIXED (adsmt-theory `arith.rs`, commit `417507b`): direction-symmetric `existing_dominates` (the LE/GE symmetry the USER flagged — neither direction dominates the other), `norm_two_var` normalizes `≥`/`>`→`≤`/`<` mirror (uniform FM direction), `var_diseq_conflict` + `var_diseqs` recording (additive — UF still owns the diseq). **Re-validated with a NEW randomized two-var-focused z3-differential: ~4400 LIA cases ×5 seeds → 0 false-unsat, 0 false-sat.** LESSON (reinforces [[feedback_z3_differential_for_unsat_trust]] + [[feedback_roundtrip_through_real_producer]]): a differential corpus is only as good as the SHAPES it generates — the bare two-var chain was a blind spot; the order-law work organically produced it. So the broad "lu-conservative" claim holds for the SMT-LIB fragment AS RE-VALIDATED, but only after this two-var false-sat class was closed.
